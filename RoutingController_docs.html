1. סקירה כללית

RoutingController.java הוא השרת ה-API המרכזי של מערכת FAST. הוא מריץ HTTP Server פשוט (ללא Spring/Framework חיצוני) שמאזין לבקשות מהפרונטאנד (React) ומספק את כל לוגיקת העסקים.

השרת מאזין על פורט 8082 (ניתן לשינוי דרך משתנה סביבה PORT) ומגדיר 9 נתיבים שונים.

הקשר לפרויקט: הפרונטאנד (React / Vite) שולח בקשות HTTP לשרת הזה. השרת מחזיר JSON עם מסלולי נסיעה, מצב אמבולנסים, מקרים פתוחים, ועוד. כל ה-state של האפליקציה נשמר ב-DataStore (Singleton בזיכרון).

2. ארכיטקטורה ורכיבים מרכזיים

🗄️

DataStore (DS)

Singleton שמחזיק את כל הנתונים בזיכרון: אמבולנסים, משתמשים, מקרים, no-go zones, sessions. כל ה-Handlers ניגשים אליו.

🗺️

FastRoutingEngineClient

לקוח לקריאת גרף הכבישים מקובץ OSM. נטען פעם אחת בעת הפעלה. מחזיר מסלולים, מצב תנועה, ואינדקס רמזורים.

🔀

אסטרטגיות ניתוב

EmergencyRoutingStrategy – מסלול מהיר, עובר ברמזורים.
RoutineRoutingStrategy – מסלול רגיל לפי חוקי תנועה.

🔐

Session Management

לאחר Login מוצלח, השרת מייצר UUID ייחודי כ-token ושומר אותו ב-DataStore. הפרונטאנד שולח אותו ב-header.

🌐

CORS

כל תגובה כוללת headers של CORS כדי לאפשר לפרונטאנד (שרץ על פורט אחר) לתקשר עם ה-API בלי חסימות דפדפן.

📦

GSON

ספריית Google GSON משמשת לסריאליזציה/דסריאליזציה של JSON. כל בקשה ותשובה עוברות דרכה.

3. פונקציות עזר (Utilities)

hashPassword(String plain) אבטחה

מצפינה סיסמה טקסטואלית באמצעות PBKDF2WithHmacSHA256 עם salt רנדומלי של 16 בתים ו-65,536 איטרציות.

הפלט הוא מחרוזת בפורמט: base64(salt):base64(hash)

כך ששתי סיסמאות זהות יניבו hash שונה בכל פעם, ולא ניתן להפוך את ה-hash לסיסמה המקורית.

verifyPassword(String plain, String stored) אבטחה

מאמתת סיסמה מול ה-hash השמור. מחלצת את ה-salt, מריצה שוב את PBKDF2 עם אותו salt, ומשווה בתים.

תומכת גם ב"סיסמאות ישנות" (ללא :) לצורך תאימות לאחור עם הנתונים הראשוניים.

cors(HttpExchange ex) HTTP

מוסיפה שלושה headers לכל תגובה כדי לאפשר Cross-Origin Requests:

  • Access-Control-Allow-Origin: * – מאפשר לכל דומיין לגשת
  • Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS
  • Access-Control-Allow-Headers: Content-Type,Authorization
handleOptions(HttpExchange ex) HTTP

מטפלת ב-Preflight CORS requests. הדפדפן שולח OPTIONS לפני כל בקשה "מורכבת" (POST עם JSON).

מחזירה true אם הבקשה הייתה OPTIONS (וטופלה), false אחרת – כך כל Handler יכול להשתמש בה בשורה ראשונה.

sendJson(HttpExchange ex, Object data) HTTP

מסריאלת כל אובייקט Java ל-JSON דרך GSON, מגדירה Content-Type: application/json, ושולחת תגובה עם קוד 200.

body(HttpExchange ex) HTTP

קוראת את גוף הבקשה (POST/PUT) ומפרסרת אותו כ-JsonObject. מחזירה אובייקט ריק אם הגוף ריק.

queryMap(String query) HTTP

ממירה query string (?lat=32.1&lon=34.9) ל-Map<String, String> נוח לשימוש. מבצעת URL-decode.

4. כל ה-Endpoints מפורטים

RouteHandler GET /api/route

ה-endpoint המרכזי של הפרויקט – מחשב מסלול ניתוב בין שתי נקודות.

פרמטרים (Query String)

שםסוגתיאור
startLatdoubleקו רוחב נקודת מוצא
startLondoubleקו אורך נקודת מוצא
endLatdoubleקו רוחב יעד
endLondoubleקו אורך יעד
isEmergencybooleanהאם מדובר בניתוב חירום?

לוגיקה

1
בחירת אסטרטגיהאם isEmergency=true → EmergencyRoutingStrategy (מסלול מהיר, רמזורים). אחרת → RoutineRoutingStrategy (חוקי תנועה רגילים).
2
חישוב מסלולהקריאה ל-engine.getOptimalRoute() מחזירה RouteResponse עם קואורדינטות הנתיב וזמן הגעה משוער.
3
בדיקת No-Go Zones (חירום בלבד)אם מסלול החירום עובר דרך אזור חסום (פיגוע, אירוע ביטחוני וכו'), מחשב מחדש עם אסטרטגיה רגילה כ-Fallback.
SignalsHandler GET /api/signals

מחזיר את מיקומי כל הרמזורים (Traffic Signals) מגרף ה-OSM. הפרונטאנד מציג אותם על המפה כשכבת מידע.

הנתונים מגיעים ישירות מ-ENGINE_CLIENT.getSignalIndex().getAllSignals().

TrafficHandler GET /api/traffic

מחזיר שכבת תנועה (Traffic Overlay) עם מידע על צפיפות כבישים ועיכובים. משמש להצגה ויזואלית על המפה.

LoginHandler POST /api/auth/login אותנטיקציה

נקודת הכניסה של כל המשתמשים (נהג, מוקדן, מנהל). מקבלת username ו-password.

זרימה

1
חיפוש משתמשDS.getByUsername(username) – מחזיר null אם לא קיים.
2
אימות סיסמהverifyPassword() מאמתת מול ה-hash. אם נכשל → 401 Unauthorized.
3
יצירת SessionUUID רנדומלי נשמר כ-token ב-DataStore, ומוחזר ללקוח יחד עם role, userId, ambulanceId, displayName.

הפרונטאנד שומר את ה-token ב-localStorage ושולח אותו בכל בקשה עתידית.

EtaHandler GET /api/eta

מחשב זמני הגעה לכל האמבולנסים הזמינים לנקודת יעד נתונה – גם בניתוב רגיל וגם בחירום. זהו "ETA Intelligence".

לוגיקה

1
סינון אמבולנסיםרק אמבולנסים עם סטטוס available ועם נהג משויך נכנסים לחישוב.
2
חישוב כפוללכל אמבולנס מחושב ETA בשתי האסטרטגיות – רגיל וחירום – במקביל.
3
תוצאהמחזיר מערך עם routineEtaSec ו-emergencyEtaSec לכל אמבולנס. המוקדן יכול לבחור את הטוב ביותר.
UserHandler GET /api/users POST /api/users DELETE /api/users

ממשק CRUD למשתמשים – בשימוש על ידי ה-Manager Suite.

  • GET – מחזיר רשימת כל המשתמשים (ללא סיסמה) עם role ו-ambulanceId
  • POST – יצירת משתמש חדש. אם ה-role הוא driver, נוצר DriverUser מיוחד עם מספר אמבולנס. אם האמבולנס המשויך לא קיים, הוא נוצר אוטומטית.
  • DELETE – מחיקת משתמש לפי id
שים לב: בעת יצירת נהג, הסיסמה עוברת דרך hashPassword() לפני השמירה – הסיסמה הגולמית לעולם לא נשמרת.
NoGoZoneHandler GET /api/nogozones POST /api/nogozones DELETE /api/nogozones

ניהול אזורי חסימה (No-Go Zones) – אזורים גיאוגרפיים שניתוב חירום אסור לעבור דרכם.

  • GET – מחזיר את כל האזורים הפעילים
  • POST – יצירת אזור חדש עם שם, גבולות גיאוגרפיים (minLat/maxLat/minLon/maxLon), סוג (קבוע/זמני), וחלונות זמן (dailyStart/End לחסימה יומית, onceStart/End לאירוע חד-פעמי)
  • DELETE – מחיקת אזור

כשמחושב מסלול חירום ב-RouteHandler, כל נקודה במסלול נבדקת מול אזורים אלו.

5. זרימת בקשה מקצה לקצה – דוגמה: שיגור אמבולנס

1
מוקדן יוצר מקרהפרונטאנד שולח POST /api/cases עם כתובת, קואורדינטות, ורמת דחיפות.
2
קבלת ETAמוקדן מבקש GET /api/eta?endLat=X&endLon=Y – מקבל טבלה עם כל האמבולנסים וזמני הגעה.
3
שיוך אמבולנסמוקדן שולח POST /api/cases/assign – מחבר את המקרה לאמבולנס הנבחר.
4
חישוב מסלול לנהגאפליקציית הנהג שולחת GET /api/route?isEmergency=true – מקבלת קואורדינטות מסלול ו-ETA.
5
עדכוני מיקוםבכל כמה שניות, הנהג שולח POST /api/ambulances/location – המוקדן רואה את המיקום בזמן אמת.
6
הגעה וסיוםהנהג שולח POST /api/cases/arrive בהגעה, ו-POST /api/cases/complete בסיום הטיפול.

6. אבטחה

🔑

PBKDF2 Password Hashing

הצפנת סיסמאות בתקן מקובל עם salt רנדומלי ו-65,536 איטרציות. עמיד מול brute-force.

🎟️

UUID Session Tokens

כל login מייצר token ייחודי. הפרונטאנד שולח אותו בכל בקשה. מאפשר logout ע"י מחיקת ה-token.

🌐

CORS Headers

מוגדר כ-* (כל דומיין) לפיתוח. בסביבת ייצור כדאי לצמצם לדומיין הספציפי של הפרונטאנד.

⚠️

הגבלות נוכחיות

אין JWT מלא. אין rate limiting. ה-DataStore בזיכרון (נמחק בהפעלה מחדש). מתאים ל-Demo/POC.
